What changed since v2

If you built v2, three things move. Everything else — buttons, LCD, audio, the Morse table — is untouched.

v2v3
Motor driverTB6612FNG, 4 GPIO pins3-pin module, 1 GPIO pin
Motor supply5V3.3V
Child Mode lightnoneLED strip via relay on GPIO16
Brakingactive brakecoast, ~30ms

The motor change frees GPIO6, GPIO13 and GPIO26. Losing the active brake costs nothing here: the eccentric mass stops well inside one Morse time unit, so the pattern still reads correctly.

01

Flash the SD card

In Raspberry Pi Imager: device Raspberry Pi 4, OS Raspberry Pi OS (64-bit). 64-bit is not a preference — soundfile has no 32-bit ARM wheel, and the system libsndfile on older releases cannot decode MP3 at all.

Under Customisation set hostname sarswela, the same username and password, SSH enabled with password authentication, and the Wi-Fi credentials for whichever network the Pi will join.

Copy the SSID by hand, character for character

A hotspot named Mi 15T is not Mi15T. One missing space costs an evening — the Pi boots fine and simply never appears on the network, with nothing to read because you have no monitor. Force 2.4GHz and WPA2, and turn hotspot power saving off; it shuts down when nothing is connected, and first boot takes minutes before the Pi even tries to join.

After writing, Windows offers to format the card because it cannot read the Linux partition. Close that dialog — formatting wipes the OS you just wrote.

02

Find the Pi and connect

Boot and wait. First boot resizes the filesystem and reboots itself, so give it three or four minutes before expecting anything.

ssh sarswela@sarswela.local

If mDNS does not resolve, find the address from the hotspot's client list and use it directly:

ssh sarswela@192.168.137.113
Nothing appears at all

Re-flash rather than debug blind — you cannot read the Pi's logs without a monitor, and a wrong SSID looks identical to a dead card. If a re-flash also fails to appear, suspect the card itself: check Windows Disk Management, and if the card does not enumerate there, it has failed at hardware level and no amount of re-flashing will help.

03

Get the code onto the Pi

Run scp from a terminal on your laptop — not inside the SSH session. This is the single most common mistake: from the Pi's shell, D:\... is not a path, and scp reads D: as a hostname and reports Could not resolve hostname d.

scp -r "D:\path\to\pikapatid_v3\*" "sarswela@192.168.137.113:~/sarswela/"

Quote both arguments. Paths with spaces break otherwise, in ways whose error messages point nowhere near the real cause.

Then, back in the SSH session, confirm what landed and when:

ls -la ~/sarswela/*.py
date

Compare the file timestamps against date. A file dated yesterday means the copy silently failed and you are about to debug code that was never transferred.

04

Install and verify

cd ~/sarswela
chmod +x setup.sh && ./setup.sh

setup.sh creates the virtualenv, installs dependencies and enables I2C. Then run the tests before touching any hardware:

./venv/bin/python test_logic.py

25 tests, all mocked — no GPIO, no LCD, no motor. They check mode transitions, the Morse table, the foreign-language gate, clip selection, light behaviour, and pin sanity: no duplicate assignments, nothing squatting on the I2C pins. Run these after every config edit. A duplicated pin is caught here in a second, or at 2am before a performance.

With the LCD wired, confirm it answers on the bus:

i2cdetect -y 1

You want 27. If you get 3f, set LCD_ADDRESS in config.py to match. Nothing at all means I2C is off or SDA/SCL are swapped.

VCC must be 5V, not 3.3V — a PCF8574 backpack often will not answer on 3.3V. A lit backlight with a blank screen means power arrived but nothing wrote to it, which is a software symptom, not a wiring one.

Stage B

Buttons — seven modes, plus shutdown

Each button bridges its GPIO to any ground pin. Internal pull-ups are enabled in software, so no external resistors.

English, Spanish and Mandarin do nothing until Foreign has been pressed. That gate is deliberate — it mirrors foreignGate in the original sketch — so a language button that "does not work" may simply be behaving correctly.

Stage C

Vibration motor — three wires, no driver

ModulePiPhysical pin
INGPIO1232
VCC5V4
GNDGND39

The module carries its own switching transistor and flyback diode. GPIO12 therefore supplies only a logic signal — a few milliamps — while the motor's 80–100mA comes off the 5V rail, shared with the relay coil and the LCD. That division is what makes a direct connection safe here when a bare motor's would not be.

Never wire a bare motor to a GPIO pin

A pin sources 16mA. A coin motor wants 80–100mA and, worse, kicks back an inductive spike when it stops. Without the module's transistor and diode you are destroying the pin, possibly the Pi. If your module has only two usable pins because IN and VCC were soldered together, separate them — bridged, the motor runs permanently and its full current flows through whatever feeds that joint.

Why 5V works here, at 0.85

The 5V rail puts about 4.7V at a motor rated for 3V. Two things make that safe. Peaks do not cook motors, averages do — and with the burst texture the motor is driven only 70% of the time within an element, so a dash averages 0.85 × 0.70 = 0.60 duty, about 2.8V, just under rating. And Morse is intermittent: "Sarswela" is a few seconds of buzzing, not continuous running.

Meanwhile the peak still reaches ~4.0V, and the peak is what the skin feels. That is the entire reason to be on 5V — more amplitude per burst at no extra heating. MOTOR_SUPPLY_V in config.py ties the two numbers together, and three tests enforce it: move the rail without moving the level and the suite fails, quoting the value you should have used.

Test it alone, with the service stopped so the pin is free:

sudo systemctl stop kapatid
./venv/bin/python -c "
from gpiozero import PWMOutputDevice
import time
m = PWMOutputDevice(12, frequency=1000)
m.value = 1.0; time.sleep(2); m.value = 0; m.close()
"
sudo systemctl start kapatid
Stage D

Child Mode light — relay module

Nine LEDs draw about 160mA, ten times what a pin allows, so the strip needs something between it and the Pi. A low-level-trigger relay module does the job and isolates the strip's current completely.

Coil side — this is what the Pi drives:

ModulePiPhysical pin
INGPIO1636
VCC5V4
GNDGND34

VCC must be 5V. The SRD-05VDC-SL-C coil will not pull in reliably at 3.3V. Both 5V header pins are the same rail, so sharing one with the LCD is fine — the coil's 80mA and the LCD's 100mA sit comfortably inside the header's budget.

Contact side — the middle terminal is COM; check the silkscreen for which outer one is NO. Use NO so the strip is dark when idle, and wire the relay into the strip's positive leg:

TerminalTo
COM3.3V (pin 17), or an external supply +
NOstrip +
—strip − to that same supply's ground
Worth exploiting

Relay contacts are electrically isolated, so if you power the strip from a phone charger or power bank instead, its 160mA never touches the Pi at all — cut the strip's + line and route both ends through COM and NO. Only the coil side needs a shared ground with the Pi; the contact side needs none.

Then set the two flags in config.py to match a low-trigger part:

PIN_CHILD_LIGHT = 16
CHILD_LIGHT_ACTIVE_LOW = True

Set PIN_CHILD_LIGHT = None to disable the light entirely — useful while the relay is not yet wired, since the code then never touches GPIO16. If you swap the relay for a ULN2003 channel or a plain NPN transistor + 1kΩ base resistor, set CHILD_LIGHT_ACTIVE_LOW = False: both light the load on a high pin, draw under a milliamp, and make no noise.

Lit constantly, or inverted? The wire is on NC instead of NO. Move it to the other outer terminal rather than inverting the flag — the flag should describe the part, not paper over the wiring.

Stage E

Audio — the 3.5mm jack

Powered speaker or headphones into the jack. Confirm the output device and raise the level:

aplay -l
amixer sset 'Master' 90%
Do not enable hardware PWM

The 3.5mm jack is the PWM peripheral. Setting PWM_MODE = "hardware" claims it and the audio stops. Leave it on software — thread-timed PWM is entirely adequate, since an eccentric mass has 20–50ms of mechanical inertia and cannot respond to timing jitter anyway. A test enforces this combination is never configured.

06

Autostart on boot

So the device runs without a laptop:

sudo cp kapatid.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now kapatid
sudo systemctl status kapatid

You want active (running). Anything else, read the traceback — status truncates, journalctl does not:

sudo journalctl -u kapatid -n 50 --no-pager

The unit sleeps 5 seconds before starting, giving I2C and the audio device time to come up. Without that delay it wins the race about half the time and fails the other half, which is worse than failing consistently.

07

Making the buzz felt

A weak buzz is rarely a power problem. Amplitude is capped by the motor and the rail, but perceived strength is not — and that is where the room is.

Why a steady buzz fades

The skin receptors that sense vibration respond to change, not to sustained pressure. Hold a constant buzz and they adapt within a few hundred milliseconds: the motor is still turning at full power, and you stop noticing it. It is why a long dash can feel weaker at its end than at its start.

MORSE_TEXTURE exploits that. Instead of holding each dot and dash steady, it chops the element into a burst train at MORSE_TEXTURE_HZ. Peak amplitude is unchanged — every burst still reaches MORSE_LEVEL — but the interruptions keep the receptors from tuning it out. Element durations are preserved to within a percent, so the Morse still reads correctly.

RateFeel
10–15 HzDeep modulation, an insistent throb. Strongest sensation.
20–30 HzShallower; reads as a rough buzz.
above 40 HzThe mass cannot follow. Feels steady again — no gain.

The eccentric mass needs 20–50ms to spin up or down, which is what puts the sweet spot so low. MORSE_TEXTURE_DUTY sets how much of each period is driven: lower digs the troughs deeper for more contrast, but below about 0.5 the mass never reaches speed at all.

Everything else, in order of how much difference it makes:

  1. Mounting. A motor dangling on wires has nothing to react against and feels feeble at any voltage. Bond it flat to a rigid part of the enclosure with foam tape or glue, or press it against skin. This routinely matters more than every setting below combined.
  2. MORSE_LEVEL = 1.0. At 3.3V that is inside the motor's rating, so there is no reason to hold back.
  3. Longer KICK_TIME — 0.060 — so each element opens at full power. An eccentric mass will not start from rest at low duty; the kick breaks stiction before the level settles.
  4. Raise MORSE_UNIT to 0.200 so each element lasts longer against the skin.
  5. Move VCC to 5V and set MORSE_LEVEL = 0.80. Noticeably stronger, and survivable because Morse is intermittent — but do not run 5V at 1.0, and expect to trade motor lifespan for the amplitude.
When tuning has run out

If all of the above is exhausted and it is still too weak, the motor is the ceiling rather than the settings. Some 3-pin breakouts carry a series resistor that caps the current whatever voltage you feed them — look for a small resistor between the transistor and the motor terminals. A bare 10mm motor switched through the relay, or a physically larger ERM, is the answer for anything that has to be felt through clothing.

After any edit, restart and re-test:

./venv/bin/python test_logic.py
sudo systemctl restart kapatid

09

When something breaks

Service will not start

Read the traceback first. Guessing from symptoms costs more than the thirty seconds of reading.

sudo journalctl -u kapatid -n 50 --no-pager

GPIOPinInUse: pin GPIO16 is already in use

Two objects claiming one pin inside one process. Almost always a duplicated line:

grep -c "hardware.Light()" kapatid.py

The answer must be 1. If it is 2, delete the extra. Also check no other process holds the pin, and stop the service before manual tests.

The light lags the button

Three delays stack up, and the light used to sit behind all of them. BOUNCE_TIME is paid on every press before anything downstream runs; cancelling a Morse sequence joins its thread; and the LCD's I2C write pushes 32 characters at 100kHz. Setting a GPIO costs microseconds by comparison, so in v3 the light is updated first in on_press() — before the Morse cancel and before the LCD.

If it still lags, lower BOUNCE_TIME, but not below about 0.02 or one press starts registering twice.

Relay pulls in but never releases

Not a wiring fault, and no amount of rewiring fixes it. A low-level-trigger module running its coil from 5V expects its IN pin driven near 5V to switch off. A Pi pin reaches only 3.3V, which can leave the module's input transistor partly conducting — so it energises willingly and then never fully lets go.

The fix is an NPN transistor instead, which switches on a high signal and so has no threshold to fall short of: GPIO16 through a 1kΩ resistor to the base, strip − to the collector, Pi GND to the emitter, strip + to 3.3V. Then set CHILD_LIGHT_ACTIVE_LOW = False.

LCD backlit but blank

The program is not running. Power reached the backpack; nothing wrote to it. Check the service status — this is not a wiring fault.

Motor silent, but the LCD changes mode

The logic is fine and the button works, so the fault is downstream. Test the motor alone with the Stage C snippet. If it buzzes there, the wiring and pin are good and the problem is config. If it does not, it is the module, its supply, or the joint.

Old code keeps coming back

unzip -o over the working directory reverts every file to the archive's version, silently discarding your edits. Commit first, and prefer git checkout for restores:

git add -A && git commit -m "working config"

No audio

aplay -l
amixer sset 'Master' 90%

Then confirm PWM_MODE is software. Hardware PWM silences the jack.

LCD not on the bus

i2cdetect -y 1 empty means I2C is disabled or SDA/SCL are swapped. Enable it in sudo raspi-config → Interface Options → I2C. If it reports 3f, set LCD_ADDRESS to match.

10

Before a performance

  1. Boot from cold, on the real power supply, with no laptop attached. Booting from a laptop's USB port and then unplugging it is not the same test.
  2. sudo systemctl status kapatid — active (running).
  3. Press all eight buttons in turn. Watch the LCD, listen for each clip, feel the motor on Deaf, watch the strip on Child.
  4. Press Foreign, then each language. Then press a language without Foreign first and confirm it is correctly ignored.
  5. Press Deaf, then interrupt mid-Morse with another button. The buzz must stop immediately.
  6. Check the motor is still firmly mounted. Adhesive fails, and a loose motor feels like a dead one.
  7. Leave it running for ten minutes untouched, then press a button. Nothing should have drifted or died.
Keep a known-good card

Image the working SD card and keep the image. Cards fail without warning — one died mid-build here, and no amount of re-flashing brought it back. A spare card with a known-good image turns that from a lost evening into five minutes.
